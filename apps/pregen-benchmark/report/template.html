Benchmark report · TypeGPU 0.12.7

TypeGPU at runtime vs. WGSL pregenerated with tgpu.resolve

Some teams resolve all their TypeGPU shaders to WGSL at build time so they don't ship the library. We rebuilt four docs examples both ways to see what that buys, then made the runtime path cheaper.

Summary

  • Pregenerating saves 78–90 kB of gzipped JS per app: everything except a few kB of host code and the WGSL strings. On the mobile profile that alone is 470–600 ms before any app code runs.
  • The first frame arrives 0.7–1.1 s later with runtime TypeGPU on mobile (median per example), from download, parsing, and generating WGSL on the main thread. Runtime variants also show 130–310 ms of total blocking time on mobile; pregenerated ones show almost none.
  • The optimized TypeGPU ships 6.2% less gzipped JS (5.5–6.3 kB per app). On mobile it reaches the first frame 18–130 ms sooner in all four examples and blocks the main thread up to 70 ms less (slime-mold-3d unchanged). CPU-side vector math and buffer writes got several times faster: jelly-slider spends a quarter of the JS time per frame it used to (42.5 → 10.5 ms on mobile).
  • What's left is structural. The shader generator and the root object's reach account for most of the remaining gap; see the last section.

What was compared

Four examples from the TypeGPU docs were extracted into standalone Vite apps, each in two variants:

  • Runtime: the docs example as written, with typegpu (and @typegpu/noise / @typegpu/sdf where used) bundled and shaders generated in the browser. Measured against the published 0.12.7 build and against the optimized build from this work.
  • Pregenerated: the same shaders, resolved to WGSL at build time with tgpu.resolve (through unplugin-typegpu), and host code written against the raw WebGPU API. No TypeGPU code reaches the browser.

Both variants share the same controls UI and instrumentation code.

JavaScript shipped

Total JS of each production build (Vite 8, default minifier), compressed with gzip level 9. This is what crosses the network.

The pregenerated builds of slime-mold-3d and jelly-slider are larger than boids' because they bundle wgpu-matrix (as do their runtime builds) and carry their WGSL as strings: jelly-slider's shaders are about 29 kB of text before compression.

Loading: first frame and first interaction

Medians of cold loads each (fresh browser context, cache disabled, one discarded warm-up). The mobile profile approximates Lighthouse's: 4× CPU slowdown, 1.6 Mbps down / 150 ms RTT. Desktop has no throttling.

On the mobile profile the runtime variants start executing app code 470–600 ms after the pregenerated ones, which is the extra download and parse. Generating WGSL then adds a main-thread task of 180–280 ms before the first frame. The optimized build trims both a little; most of the gap remains.

Per-frame JS is where the optimizations show most, in apps that do CPU-side vector math: jelly-slider's slider physics builds many vectors per frame. The remaining per-frame difference to pregenerated code is largely TypeGPU submitting each pass separately, while the hand-written stable-fluid and slime-mold-3d variants record a frame into one command encoder.

We also measured when a scripted click on the first control gets handled (see the table). On SwiftShader that number mostly reflects when the emulated GPU releases the main thread after the first submit, so it sometimes favors the runtime variant. It's reported, but not charted.

All metrics

Every median, per profile. "First interaction" is when the example's handler received a click that a scripted user sent as soon as the first control was visible; "input delay" is how long that click waited for the main thread.

What changed in TypeGPU

Every change keeps the public API and the generated WGSL unchanged; the typegpu test suite passes as before. They're on the perf/typegpu-load-time branch.

Dropped the typed-binary dependency

TypeGPU used four small classes from it, but the package ships impure top-level code (schema instances, compiled class fields), so bundlers kept all of it. A ~200-line internal reader/writer replaces it.

−12.9 kB minified · −2.9 kB gzip in every app
Marked dualImpl, struct and a signature helper as free of side effects

Bundlers dropped the unused std bindings but kept the dualImpl({…}) calls that created them, along with their CPU implementations. With /*#__NO_SIDE_EFFECTS__*/ (already used elsewhere in the package), unused std functions now disappear: 54 dead calls in boids.

−17.4 kB minified · −3.3 kB gzip in boids
Console-log serializers are created on first use

About 30 tgpu.fn objects for shader-side console.log were built on import, in every app, logging or not.

TypeGPU module evaluation 47 → 39 ms at 4× CPU (boids)
Vector components are read by name in hot paths

Reading a vector by index (v[0]) goes through the index accessors that make v[0] = 1.5 cast on assignment, and V8 handles those on a slow path: about 155 ns per read, against 9 ns for v.x. The compiled buffer writer, swizzles and the helpers behind CPU-side std functions read by index. They now read components by name, with a fallback for tuples and typed arrays in the writer.

Writing 1,000 vec2f structs: 0.67 → 0.03 ms · v.xyz: 605 → 80 ns · std.add(v2, v2): 2.7 → 0.6 µs · std.mix: 4.4 → 0.9 µs
Cheaper vector construction and CPU-side std calls

d.vec2f(x, y) copied its arguments into an intermediate array and cast each component through the callable d.f32 schema, behind a getter that allocated a fresh object. Callable schemas and std functions forwarded calls through rest/spread wrappers, and the generic component-wise helper allocated arrays per component. A scalar fast path, casting in each vector class's own constructor, bound functions instead of wrappers, and plain loops remove all of that.

d.vec2f(x, y): ~630 → ~60 ns · std.sin(x): 155 → 71 ns
No uniform-alignment analysis when its warning is off

Every $usage('uniform') computed full memory layouts to decide whether to warn about non-portable alignment, a warning that is silenced in production builds. The logger can now say whether a warning would be shown, and the check is skipped otherwise.

Less setup work per uniform buffer in production builds
Less work on shader generation's happy path

The numeric-literal check stringified the AST node for its error message on every literal; messages are now built only on failure. Each pipeline's namespace no longer copies ~500 reserved words into a new Set, function externals aren't copied when there's nothing to merge, texture views reuse their value proxy, and the hottest type guards test the cheap property first.

First generation vs. 0.12.7: 9–16% faster (boids 24.0 → 20.2 ms, jelly-slider 75.8 → 68.6 ms); later generations 16–30% faster
Opt-out build flags for unused features

Apps that never create textures or query sets, or never log from shaders, can say so with the bundler's define option (__TYPEGPU_NO_TEXTURES__, __TYPEGPU_NO_QUERY_SETS__, __TYPEGPU_NO_CONSOLE_LOG__), and the code behind those features is left out. Nothing changes for apps that don't. Not included in the measurements above, since it needs a line of app config.

boids: 274.7 → 241.6 kB minified, 77.9 → 68.5 kB gzip; mobile start ~40 ms sooner
Opt-in batching of pipeline submissions

With tgpu.init({ unstable_batchSubmits: true }), draws and dispatches made without an explicit encoder are submitted together once the frame's synchronous code is done. TypeGPU's own writes, reads and destroys submit the pending work first, so ordering is kept; a lint rule keeps future queue use going through that path. Not included in the measurements above, since it's opt-in.

Mobile JS per frame: stable-fluid 2.7 → 2.1 ms, jelly-slider 10.1 → 8.4 ms

What we tried, and where we stopped

Each of these was prototyped and measured. Shader generation timings come from interleaved runs in fresh Node processes (31+ per comparison), with all builds side by side in one directory. An A/A check showed a build's location on disk alone can shift timings by ~10%, and identical builds agree within ~2% in this setup. The hand-tuning row is where readability stops paying: rewriting call sites into lower-level code bought nothing measurable.

Where the remaining cost comes from

These are the reasons a runtime TypeGPU app stays behind a pregenerated one, even after the changes above. None of them can be fixed with local tweaks; each needs an architectural decision.

The root object reaches everything

tgpu.init() returns a root whose methods create buffers, textures, samplers, query sets, pipelines and command encoders. Bundlers can't drop unused class methods, so an app that only calls tgpu.init() and creates one buffer already ships about 320 kB (80 kB gzip). In practice every app ships the whole library, including texture uploads, mipmap generation, timestamp queries and the shader-side console.log machinery, unless it opts out of those with the new build flags (up to 12% of boids' gzip size).

The shader generator is a third of the bundle and runs cold

The WGSL generator and resolution context are 31% of TypeGPU's minified code in the boids bundle (78 of 255 kB), and 39% with std, which serves both CPU and shader code. Generation also runs exactly when it hurts most: during the first frame or the first pipeline creation, on code the JIT has never seen. In Node, the first tgpu.resolve of the boids shaders takes about 21 ms, and later ones about 2 ms. That 10× cold penalty is spread across hundreds of small functions with no single hotspot. Disabling lazy compilation doesn't remove it either, so it's interpretation and inline-cache warm-up, not parsing.

Every dispatch and draw is its own submit

Pipeline .dispatchWorkgroups() and .draw() each create a command encoder and call queue.submit. That keeps them ordered with the buffer.write() calls around them, and TypeGPU already offers batching through root['~unstable'].createCommandEncoder(). Raw WebGPU code usually records a whole frame into one encoder, which is part of why pregenerated stable-fluid (9 passes per frame) spends less CPU per frame.

Directions that would move these numbers

  • Ship host-side TypeGPU without the generator. Precompiled pipelines could take WGSL from tgpu.resolve at build time and still use TypeGPU's typed buffers, layouts and pipelines. That keeps the API's safety and drops close to a third of the library and all first-frame generation. This is what the pregenerated variants approximate by hand.
  • Make subsystems opt-in. Separate entry points or plugins for textures, query sets and logging would let bundlers drop what an app doesn't use.
  • For apps with many passes per frame: record them through createCommandEncoder() and submit once.
  • For apps: creating pipelines during an idle period, before the first frame or after the UI is wired, keeps the long generation task away from the first interaction.

Method and caveats

  • Headless Chromium 141 with WebGPU on SwiftShader (Vulkan, CPU-emulated GPU). GPU-side times, especially shader compilation and the frame rate of the heavier scenes, are much slower than on real hardware and identical between variants, since the WGSL is the same. Read the first-frame numbers for their difference, not their absolute value.
  • CPU throttling applies to the page's main thread only, not to the GPU process.
  • The static server serves gzip; brotli sizes are in the table.
  • Frame CPU time is the JS time spent inside the frame callback and the microtasks it queues, sampled after the first 10 frames. The first frame is marked once the GPU finishes the work submitted in the first frame, including submits deferred to a microtask. On SwiftShader the heavy scenes only render a handful of frames, so treat those numbers as rough.
  • The harness, examples and scripts live in apps/pregen-benchmark; node scripts/build.ts then node scripts/bench.ts reproduces the results.
